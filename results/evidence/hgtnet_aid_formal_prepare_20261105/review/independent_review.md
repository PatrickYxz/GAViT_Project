## Closed findings (original snapshot line numbers)

**[P2] Replace an invalid root first-step receipt when accepting a replayed phase.** `external_baselines/hgtnet/aid_formal_entry.py:278–284` only writes `first_refit_step.json` when that root file does not already exist. The engine deliberately emits a first-step event from its `finally` block even when its post-update check fails (`aid_formal_engine.py:106–115`). If the first refit update fails that check, the completed calibration snapshot remains valid, the bad event is preserved at the root with `post_update_checks_passed=false`, and explicit resume can correctly restart refit from the fresh initial state. The successful replay's event is saved to the new attempt but cannot replace the old root event. Completion then always fails because `_first_ok` requires the root first-refit receipt to pass (`aid_formal_entry.py:362–373,426–427`). The current attempt directory already preserves original failed evidence, so the root receipt should describe the accepted numerical trajectory after rollback/replay; preserve the failed copy in its original attempt and replace or explicitly select the root accepted first-step receipt. Add a narrow wrapper regression covering a failed first-refit postcheck followed by a successful resume. This is source-proven; existing standalone engine postcheck tests do not exercise the entry's root-file publication rule.

**[P2] Derive the formal-started status from durable update evidence.** `external_baselines/hgtnet/aid_formal_entry.py:492–500` copies `formal_training_started` from the initial summary, then merges observed optimizer steps and `training_started`, but never merges the formal flag. The summary is initialized with both flags false and is only rewritten at completion or caught failure. Therefore ordinary in-progress status, or status after an abrupt process death, reports `optimizer_steps>0` and `training_started=true` together with `formal_training_started=false`. A fresh stdlib counterexample using the actual `status` function, an initial `real_aid` summary, and a durable first-update packet produced `{"formal_training_started": false, "optimizer_steps": 1, "state": "incomplete", "training_started": true}`. Derive the formal flag from the real-AID update evidence and add a focused partial-run status regression. This does not affect model updates but incorrectly reports whether the paid formal experiment has begun.

**Closure review:** the new `_archive_discarded_first_steps` helper moves only root receipts whose optimizer counter exceeds the restored committed counter into the new attempt's `discarded_*` files, retaining exact bytes and committed proofs. The resumed callback invokes this before accepting replayed progress, so a new accepted first-refit proof can publish. Status now requires a validated `real_aid` binding and positive durable observed steps before deriving formal-started true; the regression explicitly keeps `cpu_fixture` false. Reviewed `entry_delivery/fix_round1/entry_fix.diff`, actual source, and `tests/test_hgtnet_aid_formal_resume_entry.py`. `entry_delivery/fix_round1/green.txt` records **14 targeted stdlib entry/status/resume regressions passing**, including the actual entry orchestration callback and real status acceptance with mocked numerical/runtime inputs. ## Material limits

This is a local implementation review. No original full AID bytes, target GPU, real 100-epoch training, full Adam/checkpoint memory peaks, full loader ETA, CUDA recovery, actual formal test metrics or paid-run costs were verified here. The historical GPU probe is a prerequisite receipt, not a formal result. CPU generated image/tensor/tiny-model tests establish local control flow/numerical behavior; status fixture files establish validator behavior. Release evidence should retain those scopes separately.

The persistent output lock is only removed in `finally`; SIGKILL or machine restart can leave a stale `.lock`. Safe explicit dead-lock recovery must be documented if recovery after abrupt process or machine termination is promised. This is recorded as an operational limitation, since the design requires mutual exclusion but does not specify automatic stale-lock deletion.
